## 为什么不能只靠看

凭肉眼看只能得出「用了大图和柔和的光」这种没法落地的结论，而且**大概率是错的**：
一个 2.7 秒的缓动交叉溶解，肉眼会读成「每 2.5 秒换一张、淡化 0.6 秒」——差了四倍多，
而这个错误结论已经写进过交付文档。

| 想知道 | 怎么测 |
|---|---|
| 背景是视频、Lottie 还是几张静态图 | 读安装包的资源清单 |
| 过渡多长、曲线什么形状 | 录屏逐帧差分 |
| 渐变有没有颗粒、能不能纯 CSS 画 | 相邻像素差统计 |
| 光斑中心在哪 | 降采样网格上的色度峰值 |
| 文字放上去对比度够不够 | 对实测极值做 WCAG 计算 |
| 端侧还是云端、买了哪些 SDK | 包内原生库、域名和接口路径 |

**能测的一律测，不能测的标明是推断。这个区分就是全部价值所在。**

以及这张图本身是怎么做出来的：

## 怎么用：说人话就行

不用记命令。你说你想要什么，它听的是这三个入口：

| 你说 | 它做什么 |
|---|---|
| 「分析一下 XX 的登录页」「那个背景是视频还是静态图」「这个转场多长时间」 | **拆一屏** → 机制 + 能照着做的数值 |
| 「我要做空状态页，没思路」「同类产品的 onboarding 都怎么做」 | **找三个参考**（web + App 混合）→ 各自机制、共同点、分歧点、建议走哪条 |
| 「我们要做自动分章节，先调研一下」「他们的转写是端侧还是云端」 | **调研一个功能** → 需求分析 + 功能分析 + 技术剖解 |

下载安装包、在别人 App 上操作产生数据、往任何地方写文件之前，**都会先问你**。

```bash
ln -s "$PWD/how-they-built-it" ~/.claude/skills/how-they-built-it
```

> 分析一下 XX 的登录页是怎么做的，我们的比它差太多

## 看结论要看标签

每条结论都挂证据标签，标签不是装饰：

- **`[真机]`** —— 你亲眼看到，附录屏时间点
- **`[包内]`** —— 追溯到具体文件。只证明**这些字节在包里**，
  ⛔ 不证明功能上线了、可达、或对所有用户可见
- **`[推断]`** —— 证据撑不住这句话，**包括「两个标签都有、但它们只支撑一个更弱的结论」**

⭐ **架构类结论默认 `[推断]`**，哪怕两个标签都齐。「没有端侧推理库」+「飞行模式下不可用」
仍然推不出「识别在云端」—— 本地识别一样可能卡在联网校验上。这一条是十五轮对抗性评审的产物。

## 手工跑

每一步都是你可以自己执行的脚本：

```bash
python3 scripts/preflight.py                    # 先看缺什么

adb shell pm path com.example.app               # 已装的最好，零下载
adb pull <每一条路径> .

python3 scripts/apk_assets.py base.apk --screen login        # 这一屏是什么做的
python3 scripts/feature_probe.py *.apk --keyword transcri    # 这个功能是什么做的
                                                             # ⛔ split 要全传，
                                                             #    原生库从不在 base.apk 里

adb shell am force-stop com.example.app                      # 冷启动，先起录屏
adb shell screenrecord --time-limit 20 /sdcard/rec.mp4 && adb pull /sdcard/rec.mp4 .

python3 scripts/frame_diff.py rec.mp4 --suggest-crop         # 动效怎么动的
python3 scripts/image_probe.py bg.png --grid 9x20 --contrast '#1E2C28'
```

⚠️ 日志采集的命令比看起来讲究（顺序、设备时间、引号都会翻车），完整写法见 `references/feature-research.md` §C.2。

`references/` 里是其余部分：`pitfalls.md`（30 条踩坑）、`feature-research.md`（功能调研全流程
与证据标签制度）、`web.md`（web 产品的规格是明文可读的，路径短得多）、`android.md`（真机与取包命令）。

## 边界

本项目用于理解**实现机制**，从而把自己的东西做得更好，**不是**用来拿别人的成果。

取安装包分三档：设备上已装的直接 `adb pull`（首选，零下载）；没装的**经授权后**
可以从公开渠道下载免费安装包，下完必须核 versionCode；
⛔ 绝不替用户登录商店账号、绝不下付费应用或绕地区限制。
⛔ 不提取竞品素材用于我方产品，也不把竞品素材提交进仓库。
⛔ 不绕付费墙、不改客户端、不规避 DRM —— 本工具只读公开分发的安装包。

## 最有价值的文件是踩坑清单

`references/pitfalls.md` 三十条里绝大多数是真实发生过的错误（个别是设计时识别的风险，
条目里会说明）：把引导页的视频当成登录页方案（犯了两次）、从 1fps 抽帧估读动效节奏、
用文件体积推断有没有颗粒、把竞品的产品特征画进自家的规格表。

第 9–14 条来自把脚本放到没见过的 App 上跑，六条里有五条**是脚本自己错**而不是分析者错 ——
一个 `ble` 子串匹配上了 `drawable`，把某 App 2886 个资源里的 1976 个塞进了「设备」桶；
对比度检查拿标题去和它自己的像素比；给一个从不重复的序列报出了「周期长度」。
**第 30 条来自做本 README 顶部那张图**。每一条现在都由 `scripts/test_regressions.py` 里的
一条样本钉住。

## 已知限制

明说，因为一个夸大自己能力的拆解工具是最糟的那种。

**只支持 Android，iOS 是明确的非目标。** iPhone 上没有 adb，
资源清单这一步 —— 也就是真正能定「视频还是五张图」的那一步 —— 整条链路不成立。
iOS-first 的 App 只剩动效分析和像素分析。

**录屏是变帧率的。** `adb shell screenrecord` 没有 `--fps` 选项，只在画面变化时出帧
（实测：静止屏录 2 秒只得到 1 帧），却照样把文件标成 `r_frame_rate=30/1`。
在平坦渐变上，重采样的假象会长得像真实运动。脚本现在能识别并告警（第 30 条踩坑），
但告警的价值取决于你愿不愿意重跑。

**缓动转场的时长读数偏短。** 对着一段已知 2.7 秒的交叉溶解实测，报出 2.16–2.38 秒，
差额落进相邻的静止段。**转场时长当下界看**。`cycle length` 不受影响，要报数字就报它。

**细微运动需要更高的分析分辨率。** `frame_diff.py` 先降采样再差分，
1080px 画面上 3px 的漂移在默认分辨率下只有 0.3px，会被平滑掉。
它会告警让你调高 `--res`，但它解析不出来的东西就是检测不到。

**对比度要喂背景图，不是截图。** 截图上最暗的「背景」像素其实是正文字本身。
而且只要文字和背景之间有任何蒙层，这些数字都不是上线值。

**Split APK 要看你问什么。** *视觉*拆解 `base.apk` 通常就够（六个 App 实测覆盖 99% 以上
资源体积）；*功能*拆解则永远不够：原生库全在 `split_config.<abi>.apk` 里。
`feature_probe.py` 接受任意多个包，报告里要写清你实际拿到了哪些 split。

**屏幕分桶是关键词启发式。** 当线索看，别当清单，用**你自己产品的词汇**去 grep 完整路径。

**从拆解到你自己的设计，那一步还是你的。** 它产出的是「别人怎么做的」的规格。
哪些适用于你的产品、哪些应该刻意做得不一样，是工具给不了的判断。
